## Context
WP-0.5's goal names "correlation id, idempotency header" as conventions to fix before
code spreads. Section 9.2 requires every mutating endpoint to accept an idempotency key
header and puts `correlation_id` inside the error envelope; Section 17 propagates the
correlation id from clients and bridge through backend and worker; ADR-012 commits to
idempotency keys plus lease fencing on all agent mutations. This task writes the single
convention that backend (WP-1.1), bridge (WP-2.3) and the clients will implement
against.

## Inputs / Prerequisites
* Parent plan Section 9.2 — idempotency key header on all mutating endpoints;
  `correlation_id` field in the error envelope.
* Parent plan Section 17 — correlation id propagated from clients and bridge through
  backend and worker, with token/secret scrubbing.
* Parent plan Section 9.6 — every state-changing action writes an Event row (events
  carry actor; correlation belongs in logs/events per 12.5 audit trail).
* Parent plan Section 10.10 — bridge: all mutating calls carry idempotency keys;
  retries with backoff.
* Parent plan ADR-012, NFR-12 — claim, checkpoint, submit and decision endpoints safe
  to retry.
* MT-0.5-02 — the error envelope whose `correlation_id` field this task defines.

## Scope (in)
* Publish the headers section of the WP-0.5 conventions document defining:
  * **Correlation id**: canonical header name; generated by the caller (web, mobile,
    bridge) when absent, honored when present; propagated through backend and worker
    into structured logs, events, audit entries and the error envelope; treated as
    diagnostic data, scrubbed of secrets (Section 17).
  * **Idempotency key**: canonical header name; required on every mutating endpoint
    (9.2); semantics for safe retries — same key with the same request replays the
    original outcome instead of re-executing (NFR-12); generation rule (caller-derived
    per logical operation, e.g. per bridge submission per 10.10).
* Define what the server stores for a key long enough to dedupe retries, and state how
  that window is configured (the numeric retention must follow a documented default —
  if not derivable from the plan, record it as an open point rather than inventing an
  authority).
* Distinguish these headers from SSE resume (event id, Section 9.6) so the three
  mechanisms are not conflated.
* Reference the document from backend, bridge, web and mobile package docs
  (WP-0.5 acceptance).
* Add a WP changelog note.

## Out of scope
* Implementing header middleware or idempotency storage — WP-1.1/WP-1.15.
* The concurrency/fencing half of ADR-012 (lease fencing) — WP-1.6.
* Bridge retry implementation — WP-2.3.
* Client header-sending behavior in web/mobile code — WP-4.x / WP-5.x.
* Choosing rate-limit header shapes — not specified in the plan; open question if
  needed.

## Target paths

* `backend/`, `bridge/`, `web/`, `mobile/` package docs or configs (reference added)

## Acceptance criteria
- [ ] The document fixes one canonical header name for correlation id and one for the
  idempotency key, with generation, propagation and honoring rules for each.
- [ ] Correlation id coverage matches Sections 9.2/17: envelope field, logs, events/
  audit, propagated across clients → bridge → backend → worker.
- [ ] Idempotency semantics match Section 9.2 and NFR-12: all mutating endpoints accept
  the key; retries with the same key are safe; bridge sends keys on all mutating
  calls (10.10).
- [ ] SSE resume (event id) is explicitly called out as a separate mechanism (9.6).
- [ ] The document is referenced from backend, bridge, web and mobile package docs
  (WP-0.5 acceptance).
- [ ] No header behavior is invented beyond the plan; undecided values (e.g. key
  retention window) are marked as documented defaults or open points, not facts.
- [ ] Changelog note added (Section 20.4 item 7).

## Test command

## Risk notes
* Header spellings are not fixed verbatim in the parent plan — choosing the canonical
  names is this task's deliverable; record them once and never alias two spellings
  (G-01-style drift is exactly what WP-0.5 exists to prevent).
* Idempotency-key retention has no stated default in the plan — an underspecified
  window silently breaks NFR-12 retries; flag it explicitly for owner confirmation
  rather than inventing an authoritative number.
