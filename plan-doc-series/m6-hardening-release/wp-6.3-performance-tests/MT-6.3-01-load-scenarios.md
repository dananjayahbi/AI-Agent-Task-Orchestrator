## Context
Section 18's Performance row defines the scenarios precisely: "20 simulated agents
with checkpoints every 30 s; 10,000 tasks; board load; SSE fan-out" with "Targets
from NFR-02, NFR-03, NFR-09." Section 19 (WP-6.3) lists "scenario scripts" as the
first slice. This task builds the measuring instrument — the scripts and fixtures —
so MT-6.3-02 can capture results and MT-6.3-03 can tune against a stable harness.
The scale envelope is fixed by NFR-09: 10 projects, 20 concurrent agent sessions,
10,000 tasks, 50 GB attachments, without architectural change.

## Inputs / Prerequisites
* Parent plan Section 18 Performance row — the four scenario elements verbatim.
* Parent plan Section 5.2 — NFR-02 (claim/checkpoint p95 < 300 ms locally), NFR-03
  (event delivery p95 < 2 s; push dispatch within 10 s), NFR-09 (scale envelope).
* MT-1.10-06 — the existing SSE delivery load test; reuse its latency-measurement
  approach for the fan-out scenario instead of rebuilding it.
* Local Compose stack in production topology (Section 16.1: postgres, redis,
  backend, worker, beat, web) with migrations applied.
* Section 11.1's coder flow — the API sequence a simulated agent performs (orient,
  claim, checkpoint, submit) so simulations exercise real endpoints, not synthetic
  write loads.

## Scope (in)
* Performance scenario scripts under `e2e/` (Appendix A: "scenario scripts across
  the whole stack"), each producing machine-readable results plus a summary:
  * **Agent simulation:** 20 concurrent agent sessions cycling the coder flow with
    checkpoints every 30 s (Section 18 wording), measuring per-call latency for
    claim and checkpoint (the NFR-02 clocks) against a 10,000-task database.
  * **Seed data generator:** deterministic fixture creating NFR-09's shape — 10
    projects, 10,000 tasks distributed across states/dependencies, 20 agent
    tokens/sessions — with a documented seed for reproducibility; run cost and
    cleanup documented (disposable stack or teardown).
  * **SSE fan-out:** concurrent SSE connections (web-shaped filters) receiving the
    event load generated by the agent simulation, measuring publish-to-receipt
    latency per NFR-03 — extending the MT-1.10-06 method to the fan-out count the
    scenario implies.
  * **Board load:** the API-side data path for loading a 500-card board (Section
    13.4's web target is measured by MT-4.11-04; this script measures the backend
    responses the board needs) — record the division of labor in the script header.
* Percentile output (p50/p95/p99) for every measured clock, persisted with the run
  so MT-6.3-02 records numbers, not impressions (Section 20.4 item 1).
* Threshold configuration file: the NFR-02/03 values as pass/fail inputs, clearly
  marked as plan-derived constants.
* Changelog note (Section 20.4 item 7).

## Out of scope
* Running the full suite and writing results — MT-6.3-02.
* Tuning anything the scenarios expose — MT-6.3-03.
* Push-dispatch measurement within the 10 s budget (NFR-03's push half) — see risk
  notes; the script must record what it can (sender-side dispatch) and defer the
  end-to-end device leg.
* Web rendering performance — MT-4.11-04 (WP-4.11) owns the browser-side board
  target.
* Chaos/resilience scenarios (kill worker, restart backend) — Section 18's separate
  Chaos row; not WP-6.3.

## Acceptance criteria
- [ ] Scripts implement all four Section 18 Performance-row elements: 20 simulated
  agents with 30 s checkpoints, 10,000 tasks, board load, SSE fan-out.
- [ ] The seed reproduces NFR-09's shape (10 projects, 10,000 tasks, 20 sessions)
  deterministically from a documented seed (Section 5.2).
- [ ] Claim and checkpoint latencies are measured per call — the NFR-02 clock —
  with p95 computed (Section 5.2).
- [ ] SSE fan-out latency is measured publish-to-receipt — the NFR-03 clock — per
  MT-1.10-06's method (Section 5.2).
- [ ] Every scenario emits machine-readable results with percentiles and a
  pass/fail line against the configured NFR thresholds (Section 20.4 item 1).
- [ ] Scripts run against the Section 16.1 production-topology stack with one
  documented command per scenario.
- [ ] Changelog note added (Section 20.4 item 7).

## Test command
Run each scenario against local Compose per the script docs (e.g.
`bash e2e/perf/run-agent-simulation.sh` shape — exact entry points documented in
`docs/plan/`) and confirm each emits a results file containing p50/p95/p99 and a
threshold verdict; verify the seed report shows 10 projects / 10,000 tasks / 20
sessions.

## Risk notes
* Seeding 10,000 tasks must not take longer than the measured run — if seed time
  dominates, generate once and snapshot/restore rather than reseeding per run;
  document the chosen procedure.
* "20 simulated agents" means API-level simulation of the Section 11.1 flow, not 20
  MCP bridges — say so in the script header so results are compared against the
  right baseline (the bridge adds its own overhead outside this scenario).
* NFR-03's push half (10 s) crosses FCM — a local script cannot prove device
  delivery; measure and record backend dispatch time here, and note that MT-5.10-05
  and WP-5.4's own acceptance cover the device leg (do not silently drop the
  metric).
