## Context
Section 9.2 states that all mutating endpoints accept an idempotency key header, and
NFR-12 makes claim, checkpoint, submit and decision endpoints safe to retry. ADR-012
makes idempotency keys one of the two pillars (with lease fencing) that let the bridge
retry best-effort without duplication. This slice is the bridge half of that contract:
every mutating request generated by the client carries a stable key so a retried
request is recognized by the backend as the same operation.

## Inputs / Prerequisites
* Parent plan Section 9.2 — "All mutating endpoints accept an idempotency key
  header"; the list of mutating endpoints (claim, release, checkpoints, resolution,
  audit verdict, review, transitions, sessions).
* Parent plan Section 10.10 — "All mutating calls carry idempotency keys."
* Parent plan Section 23 — ADR-012; WP-0.5 conventions document (idempotency header
  naming is settled there per Section 19.1 WP-0.5 scope).
* MT-2.3-01, MT-2.3-02 — transport and retry loop the keys must integrate with.

## Scope (in)
* Key generation: one key per logical operation (a claim attempt, a checkpoint, a
  submission), regenerated only when the logical operation changes — so a retry in
  MT-2.3-02 re-sends the identical key.
* Automatic attachment of the header on every mutating request through the client;
  GET/HEAD requests never carry a key.
* Key derivation that is deterministic within a process run (for example derived from
  the operation type and target resource plus a process-unique component), with no
  key material persisted to disk or logged.
* Unit tests proving: identical keys across retries of one operation, distinct keys
  across distinct operations, and header presence exactly on mutating verbs.

## Out of scope
* Backend deduplication semantics for received keys — WP-1.x endpoints implementing
  Section 9.2.
* Retry loop itself — MT-2.3-02.
* Retaining a submission payload locally across full process restarts — WP-2.6
  (MT-2.6-05).
* The WP-0.5 conventions document — already published; this task consumes it.

## Target paths
* `bridge/src/` (idempotency middleware/helper in the client)
* `bridge/tests/` (idempotency key tests)
* WP changelog entry

## Acceptance criteria
- [ ] Every mutating call from the bridge carries the idempotency key header named in
  the WP-0.5 conventions document; reads carry none.
- [ ] A retried operation (per MT-2.3-02) reuses the identical key; two separate
  logical operations never share a key (NFR-12, ADR-012).
- [ ] Keys never appear in logs, error messages, or committed files
  (Section 20.4 item 3).
- [ ] Tests demonstrate key stability across simulated retries and uniqueness across
  operations.
- [ ] Public contract impact checked: no OpenAPI/tool-schema change is introduced by
  this slice; if the header name differs from WP-0.5, the discrepancy is raised as an
  OQ-xx instead of silently diverging (Section 20.4 item 4).
- [ ] Changelog note added (Section 20.4 item 7).

## Test command
Run the client idempotency tests, e.g. `uv run pytest bridge/tests/ -k idempotency`;
assert identical keys across retries, distinct keys per operation, and header presence
only on mutating verbs.

## Risk notes
* Header-name drift between bridge and backend would silently disable the whole
  protection — cross-check against the WP-0.5 conventions document and the generated
  OpenAPI document (ADR-005), and raise an OQ-xx if they disagree.
* Deterministic keys derived only from operation type could collide across tasks;
  the uniqueness test is the guard.
